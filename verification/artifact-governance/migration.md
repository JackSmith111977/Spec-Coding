# 0.13.0 接入与升级说明

本页说明已经落地的组织约定；正式使用仍须从对应 Release 取得完整包和验证依据，在目标项目完成实际适配验收。候选记录不能替代发行证明。

## 首次接入

从完整包的 `harness/bootstrap/BOOTSTRAP.md` 开始。仅建立 Harness 时不需要提供业务目标，也不创建空需求或任务模板。Agent 先发现现有项目入口、空间及权限，再建立必要基线和适配记录。

新建 Repository-native 空间默认用 `spec/`；已有同名业务目录不会因此成为流程空间。Local、Shared 模式按原共享意图选择独立空间，不因导航而把资料纳入代码仓库。

接入后从实际 Agent 入口进入工作空间总入口，按相关任务或需求读取原正文和证据。任务仍以统一 `tasks.md` 或已绑定等价位置为权威；详情、摘要与日志不能另存一份可独立修改的状态。

## 从已有 Harness 升级

1. 保留当前有效包身份、本地适配、管理文件及用户修改的恢复依据。先判断哪些行为与配置受到影响，不因版本不同就全量搬目录。
2. 获取明确指定的 0.13.0 完整包，核验版本、来源、包 Hash 和对应通过依据。原包保持不变；环境转换与配置留在本地适配范围。
3. 优先复用现有空间，必要时只补总入口、角色映射和直接引用。原需求、任务、OI、代码引用及历史证据保持身份连续；不复制出平行事实源。
4. 由包内接入程序核对当前 Agent 的真实加载面。管理目录、文件存在和旧 READY 均不能代替此次相关能力验证；新增产物读取与写回约束进入实际加载链后再验收。
5. 按 Runtime 与作用域分别记录当前适配结果和限制。仅接入请求验收后结束；后续明确新业务请求可按项目事实进入 01A、01B 或恢复相应阶段，不要求已经有 Task。

## 中断与恢复

迁移前保留原绑定与可回退依据；先核对目标正文，再切换引用和入口。新旧位置并存时依据确认记录判断权威，不能按修改时间盲选或丢弃用户追加内容。

索引陈旧时回查原状态与必要依赖，不能据摘要绕过阻塞。只读角色报告缺口并交授权 Owner 修复，不以维护要求取得额外写权限。

升级失败仅恢复本次管理且获授权的变化，保护用户修改与已确认业务事实。回滚还要检查旧包是否适用于当前布局；目录迁移完成不等于新版生效，旧通过证据也不能自动证明回滚后的当前状态。

## 使用范围

规则支持渐进读取，但性能收益取决于实际项目、索引质量和 Agent 行为。是否完成不同环境兼容、效率对照与人类审阅试验，以本版本实际验证报告为准；本页不作未经实测的效率承诺。
