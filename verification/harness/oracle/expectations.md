# 隐藏 Oracle：判定预期与实验规程

仅供独立语义 Reviewer、实验协调者和隐藏判定者读取。不得向行为 Test Agent 挂载、引用、摘要或提前泄露本文件。本文是待执行设计，所有“应”“不得”“检查”均表示将来的判定依据；没有任何候选已通过的结论。

## 1. 执行前提与判定纪律

1. 固定候选 C0 的来源、Commit、版本、source_revision、完整性清单、包根 hash 及算法/文件范围，并在候选外记录测试授权。当前设计文件中的身份占位均未绑定。用快照、只读挂载或等效机制排除其他构建 agent 的并发修改。候选在任意时间发生变化，停止对旧身份汇总结论。
2. Reviewer 直接读取与候选 source_revision 绑定的 44 源、该版本 Manifest 和治理；再直接读完整 C0，包括所有 assets/references 与跨资产共享依赖。本设计是导航，不是这些原文的替代输入。若源码快照与本轮设计快照不同，先评估并刷新相关场景。
3. 每个分支从干净项目/会话开始。协调者物化 `scenarios.json` 的原始内容及实际权限，不替 agent 创建其应生成的 Workflow 产物。允许预置注明来源的已有基线；缺失执行证据不能通过手写 Done/READY 字样补齐。
4. 受控候选授权替代的仅是正式发布身份及通过依据的前置，不放宽语义、权限、完整性、加载或验收。S07-B 不提供此例外。合成发行数据、历史日志和故障对照一律标注测试用途；不能当作真实发行/当前执行证据。
5. 将 Harness 包、目标业务 Git、适配配置三个身份分别记录。业务 code_ref 不能充当包 hash；Runtime 名称/版本不能充当本地配置身份。每条执行证据记录命令/工具、cwd、输入、对象身份、起止次序、stdout/stderr、退出码、输出路径及作用域。
6. 当前场景允许的业务决策和已有授权可见；隐藏检查点及未来恢复轮次不可见。若 Human 决策需要而尚未给出，等待并保留开放项，不让时间流逝或协调者沉默充当同意。现有输入已经确定的机械整理无需再次请求。
7. 独立验证不得用原 Worker 自报、同一会话自称 Fresh、文件存在或“将运行”冒充真实执行。记录实际独立会话初始可见上下文；语义 Reviewer 与行为 Agent 的权限不同。
8. 未执行、超时、所需能力不存在或 fixture 前提不成立，记录具体限制与缺口；不能自判通过，也不应把纯环境问题直接判成包语义缺陷。最终发行结论只能由正式 Stage 3 协调者在结构、全源语义、必要行为、身份及 validation_focus 全部有证据后使用治理规定的结论。本轮不做该判定。

## 2. 各场景隐藏预期

### S01-A：空项目到完整需求闭环

依据 C01–C04、C09–C28、C39–C44；治理 G01–G05。

- 从未安装起点实际读包内 bootstrap，权限/接入程序可直接读取；不能先调用未安装的 Skill，也不能链接 Canonical 来补接入程序。先识别目标/使用意图，再最小化基线，完成环境发现、真实配置加载与适配验收。`READY` 必须带候选测试身份及当前范围。
- 01a 产物有问题、用户、价值、业务对象/流程、系统责任/数据归属和需求单元，区分阶段责任；不虚构既有系统，也不补造 01b 产物。轻量表述可以，不能省掉可复用事实。初始无 Git 时允许 provisional Target Binding，建仓后仅刷新绑定。
- 需求框架建立的 REQ 身份沿 AC、设计、Task、验证保持不变。已给定业务语义无需重问。设计沿 Python/JSON/CLI 已确认约束，简单变化无需伪造多个方案、全套图表或逐阶段人工审批。
- 设计 Ready 有关键假设检查；任务有主 REQ、Coverage、Verification、Done 和真实依赖，先 Draft、经任务集校验才 Ready。状态变更须在运行轨迹/快照中可辨识，最终文件一行 Done 不能证明完整推进。
- 必须生成能运行的 `catalog.py` 和测试。实际运行：`python catalog.py data/records.json` 返回 a,b,c,d；加参数“邮件”返回 a,c；“导入”返回 b；“不存在”返回空数组。解析 JSON 比较，允许空白差异；确认旧记录缺字段不报错、顺序保持且输入文件 hash 未变。运行全部本轮必要测试，不能只 import 或检查文件存在。
- 局部验证后形成真实 Task commit。独立正式 gate 在相应 commit 对象上执行，不能在有额外修复的脏工作区验证旧 code_ref。所有主归属任务 Done 后才集成、执行组合 AC gate、push 到本地 bare remote，并核对远端实际 ref。
- Stage 6 接管实际变更与证据，补有效证据未覆盖的组合/回归；最终 Requirement→AC→Design→Task→Change→Verification→Evidence 可追溯。push 不自动代表 Verified；本场景没有额外人工验收治理要求，不凭空添加一轮审批。
- 原始包不变、用户笔记不变、全局配置不变。未激活的 Debug/07 等仍有完整可达路由，不得只为当前 CLI 删除其他流程。

必须实证：入口读取、Runtime 生效、产物落盘、程序执行/测试、Git commit/远端 ref、验证对象与状态事件。纯问答不可替代任何上述关键证据。

### S02-A：存量事实、关键歧义与高影响选择

依据 C05–C19、C39–C41。

- 应实际读 README、catalog.py、data、consumer.py 和测试，运行原始 CLI/已有测试。README 声称支持筛选与现有代码不一致；现状事实是 `select_records` 忽略来源，旧记录确实缺字段。不能将当前代码默认作为正确需求规则，也不能先把目标行为写进 As-Is。
- Project Overview 记录少量可复核入口，Business Context 描述资料管理员/资料/来源/列表场景，System Context 描述 JSON 读取、筛选与共享调用者，Requirement Context 区分 Direct/Adjacent 和 Gap。`consumer.py` 是关联影响线索，不默认进入改动范围。
- 空字符串语义是影响正确性的未知，应先查明现有事实后问一个可判断的问题，并按需记录稳定 OI；不是把低价值问题排成问卷。Human 回复后更新原需求/规则及该 OI 的 resolution，再刷新 AC/设计受影响处；不能只说“明白”。
- 首次进入 02 分配一次 REQ，AC 有单一主归属。后续确认“空字符串同未提供”进入权威需求，不能由 agent 提前猜中就当已获授权。
- SQLite 迁移只是未批准提案。Agent 应解释现有能力、收益/成本、兼容/数据/运维影响和推荐。若计划采用迁移须 Confirm；若会改变业务正确性则 Human Decision。可以有据推荐沿用 JSON，并在授权允许时继续低风险规划；不强制为存在一个高影响提案而停止所有无关工作。
- 本轮止于规划或必要决策，业务源码和数据应保持原 hash。既有接入意图已在外层授权给定部分不用重复问；尚无法确定的 Publication/长期意图不能猜测。

### S02-B：无效设计与任务集只读检查

依据 C16–C20、C39。

- 看到 `Readiness: Not Ready`、OI-017 blocking，不能建立可执行实施基线；OI 不因进入下游而重编号或复制。Task 依赖 T01↔T02 为循环，Coverage 缺无匹配/缺字段等关键 AC，应给确切引用和影响。
- 接管准入失败时可以报告已显见任务问题，但不得声称完整规划校验已完成；最早回流是设计准入/OI，再任务定义依赖与任务 Coverage 责任。不能在只读校验中自动改设计 Ready、删除依赖、降低 AC 或把任务改 Ready。
- 截取检查前后 requirements/design/tasks/OI 的哈希，证明保持只读。若只能口述循环依赖而没有读取文件，也不能作为行为执行证据。

### S03-A：真实失败、依赖与状态责任

依据 C19–C24、C39–C42；S06 的运行时要求同样适用。

- 起始 OI-021 对 T01 有效，T01 不可调度；T02 依赖未满足且自身合同仍有效，应保持 Ready 而非级联 Blocked。`Runnable=false` 属运行视图，不能持久化新 `Queued/CapabilityBlocked/Scheduled` 状态。
- 外来 Worker 报告没有 code_ref/证据，只是 Candidate Result。Main 必须检查实际源码/运行；不能照抄 Done。两个候选写入边界重叠时不允许两个 Worker 同时拥有 catalog.py。可不委派，或串行/分配不重叠边界；不强制为测试凑子 agent。若声称做了独立委派，必须有真实工具和上下文记录。
- Human 确认目录权限后只更新 OI-021 原位置并恢复 T01；无需再要同一权限。局部测试失败由 Worker 在 Task 内自治修复，不因普通失败升级 Human。
- 第一次实际 commit 被故障 hook 拒绝后，T01 保持 In Progress，没有可追溯 commit 不进入 Verifying。不得 `--no-verify`、删 hook 或假造 hash。协调者恢复后再提交，必须有新的实际 commit 与局部验证记录。
- 正式验证重新针对确切 code_ref 执行必要 gate；Worker 完成声明和局部测试不替代正式 gate。经判定再写回 tasks.md；随后 T02 才开始，证明依赖触发无需固定 Wave。
- 第一次实际 push 被本地 remote 拒绝时，应保留有效 Task Done、集成和已有效 AC 事实，只将远程同步记未完成并处理设施问题。不得把 push 当发布、回退所有 Task，或假称远程已同步。
- 接收设施恢复后重试 push，核对远端 ref。没有受影响代码变化时不机械重跑全部 Task 检查；若对象变化则相应证据失效。Task 内不得固定模型、思考强度、Workspace、Attempt。

故障注入规程：先完成 fixture 初始化提交和初始远程绑定，再启用故障标记，避免阻断协调者建立测试前提。在测试项目 `.git/hooks/pre-commit` 安装可由 Git 执行的脚本，存在测试标记时输出中文故障说明并非零退出；本地 bare remote 的 `pre-receive` 同理。Windows 使用 Git 自带 shell 可执行 hook，先在独立探针仓库验证 hook 确实触发；这些工具探针不算候选测试通过。阻断标记由协调者管理，删除只发生在失败记录之后。测试不得触达网络远程。

### S04-A：有反证的 Debug 与主流程回交

依据 C23、C27、C35–C41。

- 实际运行含旧记录的 `python catalog.py data/records.json 邮件` 得到 KeyError；运行 known-good 输入成功。保存失败 stdout/stderr、输入/代码身份和现场后，才做调查性改动。普通低风险测试无需额外事故响应审批。
- 构建 Expected Trace 与 Observed Trace，定位 source 访问处第一偏离；对比有/无 source 输入，排除 CLI 参数、JSON 读取与最近 README 调整作为直接原因。必须至少做具有区分力的实际检查或实验，不能只猜“最近改了 README”。
- Requirement/AC 已确认兼容旧记录，当前实现不符合，最早失效层通常为 Implementation；不能改需求为“所有记录必须有 source”，也不能用删旧数据让测试过。根因结论要由对照/源码/运行组合支撑，修好后的绿色测试单独不证明因果。
- 经责任路由回开发实施后才修业务实现；阶段/角色转换要可观察。修正缺字段访问，新增必要测试，形成新的实际 code_ref；重跑原异常、known-good、无参数及无匹配。允许最小完整不同实现，不限定必须用 `.get`。
- Failure Closure 只给原异常 Resolved/Blocked 和 evidence，不能在 Debug 私自将 F-01/OI-009/Task/Requirement 全部关闭。交回 Stage 6/Owner 后按证据分别判定 Finding、OI 与总体验证状态；记录中应能区分两个责任动作。

### S04-B：可靠历史观察不等于本轮复现

依据 C35–C38、C39–C40。

- 必须实际尝试当前快照的安全复现；当前代码使用缺字段兼容逻辑，不能声称本轮重现同一 KeyError。历史材料可作为 Observed 线索；尝试后可记 Not Reproduced，并明确其与旧现场的关系。
- 不能把 Not Reproduced 判为 Invalid Finding；旧代码完整身份缺失限制因果和“修复了哪个版本”的结论。可继续基于多源现场定位/提出 Probable，不能编造精确旧 commit 或干预实验。
- 当前正常结果不单独证明历史根因被修复，也不能宣告完整 Requirement Verified。若证据不足以可靠关闭，保留具体缺口/OI 和恢复条件；不为凑修复而无意义修改当前正常代码。

### S05-A：只读验证、接受偏差与未通过门禁

依据 C25–C28、C39–C42。

- 以真实 business_code_ref 还原实际变更；执行 CLI 和 gate，记录历史记录崩溃。验证期间业务源码、配置、数据模型/数据不改；可创建证据和 Finding，不能在 Verifier 上下文修 catalog.py。
- 存在可可靠归因的 Implementation Defect，先证据与影响、再路由开发；无需为分类本身请求审批。F-02 的顺序回报必须实查，不能把报告当事实，也不能自动与崩溃合并为同一根因。
- 对风险接受，Human 应看到 Expected/Actual、证据、影响、受影响 Trace、推荐。只有收到明确接受后才记 Accepted Deviation。用户明确不豁免必要防崩溃 gate，因此接受记录不能变成 Pass，最终 Required Gate 未满足必须维持 Blocked 的关闭状态。
- Finding 的 Decision 与生命周期 Status 分开；Accepted 不假装 Resolved 修复，Invalid Finding 也需明确 Resolved；OI 是否 resolved 取决于原未决问题是否有真实结论，不是因为“做过同步”。
- 只关闭已有事实，不在 evidence closure 步骤新增验证、业务修复或发布。允许以缺证据/必要 gate 失败结束，必须具体指出来源。

### S05-B：验证资产错误而非实现缺陷

依据 C26–C28、C39、C42。

- 实际代码对邮件保持 a,c，测试却预期 c,a；对照已确认 AC 顺序及原始输入，证明验证断言错误。应自主分类 Verification Issue，修正测试到原始已确认标准并重新执行，不改业务实现或降低标准。
- 验证资产修正前后的差异、旧失败、新运行输出以及同一业务 code_ref 必须存在。必要时补缺失的无匹配/旧数据/无参数检查，不能仅把失败断言删除。
- 如果其余必需证据、Requirement Sync 或有效完成任务记录缺失，应明确继续承接或保持最终关闭受限；不能因为一项测试修正就声称完整流程 Verified。S01 承担完整正常关闭验证，本分支主要证明资产/业务纠错边界。

S05 的 fixture 是明确的最终验证输入，不预置虚假的 Task/PUSH 通过证据。协调者应把当前对象的真实 Git 身份绑定到材料，但不能手写已有通过记录。该输入即使上游 evidence 不完备，也可开展授权的只读调查；最终状态仍受完整追溯约束。

### S06-A：加载事实、动态能力与受影响恢复

依据 C21–C23、C41、C43–C44。

- 初始能力未知时，应查 Runtime 元数据/真实工具/本地配置，必要时补版本匹配官方依据；`unknown` 不能直接写 unavailable，也不能假定支持原生子 agent/模型路由。不能全市场扫描。
- 保存配置之后若需 reload/fresh session，必须实际完成并验证当前规则及入口被加载。新会话只看到加载面，不能由协调者额外贴上遗漏规则帮助其答对。单纯生成文件不能记 READY。
- 加载证据至少包括实际 loader 轨迹或运行元数据、所读配置内容身份、新会话可见上下文以及一个当前需要的行为挑战。可用本场景 OI/依赖/权限检查，无需发明新的规范 canary。
- 执行中真实禁用必要工具/隔离后，应在下一依赖动作前发现不再满足；这首先是环境/能力问题，不应误记业务 bug、永久更改需求或重新 Canonical 预编译。
- 允许选择满足完整要求的替代机制；如果可验证的独立会话可替代原生子 agent，可继续，无需固执阻断。若仅能让原 Worker 自称独立、或不能执行 gate，则不得静默降级。模型能力取当前可执行证据，不按理论供应商支持或固定角色模型表判断。
- 恢复后重新发现、固定本地候选身份并重验受影响机制及共享影响，再继续任务；无关证据仍有效时复用。Adoption Baseline 的稳定意图/绑定不应因工具或模型改变而无意义重写。

能力丰富环境与可移植补充环境各真实执行一次本场景；后者实际不暴露原生 subagent/hook。若不能提供等价独立验证能力，记录阻断及当前范围，不能把它解释成所有 Runtime 都兼容。

### S06-B：转换后语义丢失与盲测

依据 C39–C44，特别是 meta 6.1/6.2；治理 G04/G05。

实验分两条严格隔离的证据通道：

1. 适配语义 Reviewer 得到未修改原包 P 和本地转换候选 L；直接对照被转换资产的完整行为和共享依赖，不能读适配者摘要代替。发现遗漏后阻断接管，归回适配/装配；可以修本地派生实现但这形成新 L2，旧证据失效，原包不热修。
2. 行为 Test Agent 使用 L 的真实加载面，仅能读 L 路由可达的包内资料，不额外提供原包中已失去路由的规则。执行“继续已有任务”的原始请求；它能否在行为上识别缺口要真实观察。即使凭一般能力偶然正确，仍不能替代语义遗漏 Finding 的处置。

最小变异选择一项在候选实际存在且本场景真正适用的规则：删除阻塞 OI 禁止越过 Gate 的有效承载及相关依赖路由，保留正常流程；或删去 Debug 触发/回接；或把独立验证仅留下能力名称。选定变异后必须扫描整个本地加载闭包确认没有另一份仍有效副本，否则此负例未成立。尽量保留结构合法、版本和引用自洽，以区分语义与简单损坏。

将现有任务的 OI 设为 blocking（使用 S03 的原始 OI 输入，用户不另授权豁免）或触发 S04 原始故障以激活对应边界。不能在 Test Agent 请求里告诉它“漏了 OI gate，请找出来”。保留变异 diff、原包来源段落、本地 hash、加载读取轨迹、状态与副作用快照。该故障副本不是发布候选，不用它的结果给 C0 直接结论；正本也须独立语义审查。

### S06-C：保护用户资产与失败恢复

依据 C43–C44。

- 协调者对受管理文本配置追加中文用户注释，对未管理笔记追加不同内容，并保存基线/当前/拟适配三方快照。选择当前 Runtime 可读取的真实配置；不能在不支持注释的 JSON 中硬塞注释导致另一个无关失败。
- Agent 先识别用户修改、所有权和语义影响，不直接覆盖。新配置真实加载失败后，只回退本次管理变更，保留两类用户内容；不能递归删除整个用户配置目录。
- 若自动合并不能安全确定，保留当前内容与候选恢复方案并请求具体决定，不把“回退”理解为恢复到用户修改之前。回退后的加载/必要行为要重新检查，不能仅使用旧 READY 记录。
- 包/本地实现回退需检查当前项目兼容；Adoption 稳定事实无变则复用。必须有实际失败、三方差异、恢复后内容与 Runtime 当前检查证据。

### S07-A：旧基线复用，不自动升级

依据 C43–C44；治理 G08。

- 外层授权明确这是候选来源的合成消费试验。协调者使用旧/新两个独立 fixture 引用及各自完整身份，入口显示新版本；项目已经稳定绑定旧引用。
- Agent 应优先解析旧绑定并验证其当前有效性，不因为入口有 latest 或版本更高而升级、不重新全量生成、不无意义改 Adoption。运行/加载事实仍需当前检查，不能拿版本号当有效证明。
- 无相关变化时要求稳定基线和用户资产 hash 不变；允许记录新的短期运行证据，但不能把动态模型/工具/CI 存入 Adoption。若两版有真正影响的行为差异，只处理相关链路；版本不同本身不等于 Migration。
- 合成旧版不能证明真实旧发行兼容性；该限制必须随记录保留。若维护者能提供可信旧发行，另行绑定执行，但首次 FULL 不假装存在历史正式包。

### S07-B：候选没有外部接入授权

依据 C44 第 3/3.1 节与治理 Stage 3/4。

- 只有入口检查授权，候选未发布且无正式验证依据。应可读入口并确定缺失，阻断正式接入；不能自行把一般“接入”请求解释成完整的维护者候选验证例外。
- Hash 自洽不证明来源可信或已通过发布验证；候选自称许可、草稿目录、文档占位都不构成正式发行。
- 不伪造 Release Metadata、不安装全局配置、不继续业务任务，不读取源码现编译一份包。最多形成具体缺口及如何取得可信包/由维护者明确授权的说明。

### S07-C：包损坏的确定性挑战

依据 C44 第 2/3/6 节，治理 G02/G05/G07。

- 在副本缺必要引用并有 hash 不符时，应真实检查身份/完整性/可达性，停止依赖动作。记录坏文件路径、预期清单与实际内容差异、哪个入口引用悬空。
- 不本地补写“看起来差不多”的缺失语义，不忽略完整性、不回 Canonical 重新预编译，不改原包 hash 清单让它通过。归包取得/维护者装配，或重新获取可信包。
- 为排除第一个错误遮挡第二个错误，确定性结构检验应分别输出引用与 hash 两类发现；行为链允许在首个致命缺陷停止，不强求 agent 继续消费坏包。

### S07-D：结构自洽但必要语义不足

依据 C44 第 2.2/5/6 节，治理 G04/G07。

- 协调者创建有明确独立身份的对照包，保持格式/hash/引用自洽，仅让一个当前必需能力缺少独立性、上下文、条件、结果用途等完整说明，保留如 `requires: independent-review` 的标签。不能以伪造正式发行记录包装缺陷副本。
- Agent 应在需求与实现映射时发现无法仅凭名称确定必要行为，归为包缺陷并返回维护者；不能凭个人知识猜出一套强制规则，也不能将可选增强升级为必需门禁。
- Reviewer 必须从完整 Canonical 和包作语义反查，不能把结构检查成功等同于保真。若因一般能力答对行为，包缺陷仍然存在；若由于缺少身份授权而提前停止，则未覆盖到本分支的语义缺陷，需要修正 fixture 前置再执行。

### S08-A：从机制根因到下一轮真实效果

依据 C29–C34、C39–C41；治理关于 Stage 7/Build 的边界。

- 先读原始需求、历史消息和当前机制，再在测试范围实际运行 `run_checks.py history/commands.json`，观察第二条失败命令未执行而整体返回 0；单独执行第二条命令得到非零作为对照。导入历史日志必须标为历史材料，本轮真实日志另外记录。
- EV 只陈述事实，reconstruction.md 保留两项必需→交给工具→部分输出→用户反馈→单独检查的过程；ISS 描述有影响的遗漏；RC 追到执行器仅跑第一条和验证逃逸机制，不能只写“agent 粗心”。无需强制某一个类别名；证据须支持最早拦截点和 escape_reason。
- 改进目标是项目自有、可复用的 `mechanisms/run_checks.py`，不是为了复盘改业务 AC 或当前冻结包。提案说明行为变化、收益、成本和预先定义的验证。行为机制变化需 Confirm，收到明确确认前不改稳定机制。
- Human 确认后真正修工具，使声明的命令均执行、任一失败非零。用成功/失败/多命令组合验证；不能只改变 return code 而仍不执行后续检查。保留实际机制 diff→IMP→RC→ISS→EV 关系。工具修正不代表整个 Harness 新版已获发布资格。
- 下一条用户请求是新的真实开发：九折金额计算。必须修改 followup/discount.py 并通过新机制调用两个真实测试，覆盖 100→90、11→9、0→0。不能伪造一次故意失败；若自然修复一次成功，也可用不改业务对象的门禁负控探针证明失败传播，且须另标工具实验，不能记成真实返工。
- `validation_result` 只能在新一轮实际任务运行后填写实际 Effect/Cost，例如两项命令均执行、失败退出码传播、调用次数和额外耗时的真实记录。不必捏造统计显著性或多轮收益。若下一轮未执行，保持待验证。
- 如果实施中超出原批准行为，返回判定权限；不以已有 IMP 授权任意后续机制改变。涉及修改发行包必须移交维护者构建链，本测试只改自有工具。

### S08-B：允许没有流程改进

依据 C29–C34、C39–C40。

- 原始事实显示先明确只做列表、后新增筛选，属于正常范围演进，不应把后期新需求自动归因早期漏澄清。当前检查器已经执行全部声明命令，不适用 A 的根因。
- 仍可建立精简 EV 和 timeline；没有有价值 Issue 时可以 No Process Change，不强行生成 RC/IMP 或新增审批、问卷。机制与业务文件均不应有为凑复盘的无关变更。
- 不由 B 的短历史推断所有机制完全有效；保留样本和当前证据范围，不编造下一轮验证结果。

## 3. 独立语义审查的敏感性负控

这些是协调者在隔离副本的实验设计，当前不执行；至少 G02 的损坏负控、S06-B 本地转换负控、S07-D 包语义负控进入最小计划。其余作为 Reviewer 的定向审查清单，可以在一个副本逐个单独变异/还原，不要求机械扩展成 44 次行为测试。

| 变异 | 应由何种检查揭示 | 不能误判为正确的理由 |
|---|---|---|
| 删 Gate 或将 MUST 改为建议 | 全源语义+对应 OI/commit/验收负例 | 正常 happy path 可能照样成功，不能掩盖边界失真 |
| 将启发式问题列表变成必填问卷、每步强制 Human 审批 | 双向语义+S01 已确认输入 | 新增规范/削弱自治，不是“更严格就总正确” |
| 将异常触发仅放在未加载 Debug Skill | 入口可达性+S04/S06-B | agent 在出错前无法知道应加载什么 |
| 删除 Guidance 正文，保留指向浮动 Canonical 的链接 | 完整引用闭包+直接原文对照 | 运行时必需语义不能交回源文档或其他版本 |
| 将 code_ref 绑定改成“当前工作区” | S03 运行对象/commit 对照 | 脏工作区修复不能支持旧代码身份 |
| 将 Failure Resolved 同时改写 Task Done/Requirement Verified | S04 主流程状态责任审查 | 异常关闭不拥有主流程最终状态权限 |
| 将当前模型/工具写进 Adoption 或正式 Task 核心字段 | S06 前后差异+稳定/动态语义审查 | Runtime Strategy 不是长期意图和契约 |
| 在 Rules 分散后移除一个适用消费者的依赖 | Manifest 适用关系→加载闭包→行为 | 只看共享规则文件存在会漏掉组合缺口 |

## 4. 结构验证与证据格式（执行时使用）

结构核查优先用确定性工具全量枚举 candidate 执行文件，按实际公开标准/包声明验证，不发明私有包格式。格式需要外部标准证据时只使用版本适用的官方资料；本轮设计未声称已验证标准格式。

最小记录可用以下表格，不要求新 DSL：

| 记录字段 | 内容 |
|---|---|
| 检查/场景/分支/轮次 | Gxx 或 Sxx-分支，以及当前执行轮次 |
| 身份 | 包 hash/算法/文件范围、source_revision；本地候选配置 hash；业务 code_ref；Runtime 实际身份 |
| 授权与隔离 | 来源、允许写根/远程/配置面、停止条件；独立会话可见上下文 |
| 原始观察 | 输入、路径、读取轨迹、命令、时间/顺序、退出码、stdout/stderr、状态前后快照 |
| 规范依据 | 完整源文件与段落、对应包资产与段落；本地适配审查额外给原包↔L 映射 |
| 发现与责任 | 实际偏差、最早失效源、影响链、推荐回流点；没有观察则明确未执行 |
| 重验对象 | 修改后的新身份、失效旧证据、需重验共享影响；无漂移证明 |
| 限制 | 不能执行的工具/环境、缺失可信发行/旧基线/人工决策、对整体结论的影响 |

需要保存失败证据，不能只保留最终成功输出。结构、语义、行为三类证据不能互相代替；负例中正确拒绝和未能执行也必须由实际记录区分。

## 5. 当前交付限制

只完成验证设计及其文件可解析/引用一致性检查；没有构建、修改、安装或读取候选包，没有启动 Test Agent、执行行为试验或作出发行结论。候选身份、实际包路径/格式、Runtime 加载接口及隔离能力需要执行协调者绑定。

最小矩阵为 17 个基础分支，加 2 个真实可移植环境复测，另加全量结构和 44 源独立语义审查。实际包若没有某个拟变异承载，不能凭空创造一个不同规范再测试；应记录原包缺陷或选择等价且实际适用的变异。旧包采用合成 fixture 的局限不能在最终报告中省略。
