# 代码质量执行与审查

所有代码产物遵循这些原则，主要由开发实施与验证收敛消费。按项目映射到已有 Formatter、Linter、静态分析、风险匹配的独立审查或 CI；不把某个工具、语言、框架固化为通用要求，不新增流程状态或产物。

1. 可理解性：让主路径和代码顺序帮助建立正确心智模型，减少无意义回读与跳转。命名表达角色、意图、结果。复杂逻辑用有意义的中间语义降低理解成本，不做形式拆分。让关键状态、副作用、影响正确性的默认值和本层失败行为可见；不要求展开一切细节。
2. 信息质量：简单逻辑由代码表达，名字承载可复用语义，注释补非显然约束、不变量和原因。简单流程按需整体说明，独立复杂步骤用局部/块注释，易误改的非直观行为才用行注释。保留当前有效的信息；一次性旧方案、删除替换过程、可从 Task/Commit/PR 追溯的历史不写进持久注释。历史仍形成当前约束时只保留约束及必要原因。
3. 变更清晰：围绕当前 Requirement/Task 形成最小完整变更；必要修改完整覆盖目标，不机械追求最少行数。不顺手清理、重命名、格式化或重构无关代码；降低差异噪声，区分必要结构调整与真实行为变化。变更说明放 Task/Commit/PR。
4. 一致性：修改前识别相邻代码稳定命名、词汇、注释、表达惯例；质量允许时沿用，不创造无理由同义词。原则约束信息质量，项目惯例决定具体表达。不扩散损害正确性、可理解性、维护性的旧模式，也不因发现债务扩大当前治理范围。
