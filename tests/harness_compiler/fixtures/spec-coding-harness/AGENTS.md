# Spec Coding Harness Test Fixture

> This is a compiled test fixture. It demonstrates the expected repository Harness output, but it is not an active repository-wide instruction. The fixture Runtime discovers this root `AGENTS.md` only; `harness/AGENTS.md` would not be a visible output.

## Entry, source binding, and authority

Before any source-derived action, read `VERSION`, `docs/manifest.yaml`, the valid fixture `adoption-baseline.json`, its `final-workflow-route.json`, and `source-inventory.json`. Resolve every route-selected Canonical Workflow and Applicable Rule named by the inventory; the inventory is a digest ledger, not a replacement for the Canonical documents. A missing, conflicting, or stale Adoption Baseline returns work to Project Onboarding; do not infer publication, authority, or target scope.

Use the final route in order: implementation planning (`04`), development execution (`05`), then verification convergence (`06`). Follow a stricter applicable rule over a general workflow instruction. The Adoption Baseline binds this Harness only to this test fixture and permits outputs below the fixture root; it does not authorize changes outside that boundary.

Preserve Requirement → Design → Task → Change → Verification traceability. Tailor depth to risk, but never tailor away Requirement / Scope / Acceptance Criteria correctness, blocking Open Items, necessary Gates, risk-matched Evidence, authority boundaries, correction routing, or a Task Commit and `code_ref` when Git-fixed change exists. An `OI-xxx` retains one authoritative source and is not silently copied, closed, or bypassed. Risk, Finding, and Open Item are distinct facts.

Autonomous work may change only an established Contract-bound implementation detail that is reversible, verifiable, and within scope. Requirement semantics, scope, Acceptance Criteria, fixed design, Accepted Deviation, risk acceptance, and mandatory-gate waiver are Human Decision matters. For a material technical, architecture, data, or security decision, collect Evidence first and route through Confirm or Human Decision as applicable. Synchronize Human / Agent understanding only for real shared-model, authority, decision, invalidation, or major-closure triggers; update the affected Canonical fact after accepted feedback.

## Stage 04 — form a valid task set

- Accept an implementation baseline only after upstream requirement, AC, design, risk, open-item, and relevant decision facts are complete and mutually consistent. Return incomplete or contradictory handoff facts to their earliest owner.
- Decompose implementation concerns into small, independently verifiable Candidate Tasks. Preserve Requirement, Trace, Boundary, Coverage, relevant Open Item IDs, and critical paths; do not create work merely to mirror file or team boundaries.
- Formalize each Task with a stable ID, one Primary Requirement, `Draft` initial Status, Goal, Trace, Boundary, real blocking `Depends On`, Coverage, Verification, Done, and referenced Open Items. `tasks.md` is the sole authoritative Task definition and state. Keep Agent, Model, Thinking, Workspace, Attempt, Wave, and other short-lived execution metadata outside it.
- The lifecycle is `Draft → Ready → In Progress → Verifying → Done`, with `Blocked` available from `In Progress` or `Verifying`. Ready is persistent; Runnable is a runtime derivation, never a substitute persistent status.
- Bind Coverage to Verification First. Prefer deterministic Unit / Property, API / Contract, Integration, Build / Typecheck / Lint, or Browser / E2E checks as appropriate. `Done` states the real completion condition, not an activity.
- Record only genuine data, contract, capability, or verification dependencies. Persist constraints and derive scheduling or delegation strategy at runtime. A formal Task may be delegated only when its work is independent, context-isolated, verifiable, authority-bounded, and conflict-controllable.
- Validate the complete task set for Requirement / AC / design coverage, consistency, executability, dependency correctness, verification adequacy, boundedness, and absence of unresolved blocking items. Only a passing set can promote its Tasks from `Draft` to `Ready`; repair planning defects before scheduling.

## Stage 05 — execute and converge facts

- Derive Runnable only when `Status = Ready`, dependencies are satisfied, no valid blocker remains, and the needed execution environment exists. Recalculate it after every material Task or Requirement state change. Do not introduce `Queued`, `Scheduled`, or `Runnable` as long-lived Task states.
- Construct each Execution Unit from Task Contract, minimum Scoped Context, Agent / Model, Tools, Workspace, and Verification Contract. Choose sequential work for dependencies or contention; use a shared workspace only for compatible read work and isolated worktrees for independent writing work. Reduce conflicts before increasing parallelism.
- Main Agent owns global coherence, workflow state, Canonical updates, conflict resolution, and final responsibility. It is the sole writer for any one shared mutable Task / Requirement / Finding boundary at a time. Delegate bounded work, not accountability: Scout reads local facts, Researcher collects external evidence, Worker makes scoped changes, Reviewer is independent and normally read-only, and Oracle challenges drift. A Subagent returns Result, Evidence, Uncertainty, relevant Risk, and recommended next action; its result remains a Candidate until Main Agent accepts it into an existing Canonical source.
- Discover effective runtime capabilities before routing. Choose the lowest sufficient available model, thinking, tool, context, workspace, and fallback for the role and risk; do not persist those selections as Task facts. Treat capability failure, boundary failure, and authority escalation differently. A fallback that cannot meet the required capability must be explicit or block.
- A Worker confirms Task Contract, scoped context, dependency result, workspace, and verification requirements before implementation. It may inspect, hypothesize, implement, observe, diagnose, repair, and locally recheck within its boundary. Use real code and runtime evidence; keep changes understandable, truthful, minimal, consistent with local conventions, and clear in intent.
- Run deterministic local checks first. When a Git-fixed change exists, create a scoped Task Commit only after local verification and preserve a stable `code_ref`; failure to form it keeps the Task `In Progress`. A Task Commit is neither Task Done, Requirement integration, Merge, Release, nor deployment. The resulting Verification-ready Result records Task, Requirement, actual changes, result, local evidence, `code_ref` when applicable, and only relevant notes.
- Formal verification independently evaluates the Task Contract, Verification Contract, actual change, exact `code_ref` when present, applicable rules, and runtime. Worker self-check is context, not formal proof. Run deterministic Gate First; add a fresh independent Reviewer for semantic, quality, UX, or high-risk questions, but never let review replace the Gate.
- Classify failure before routing: send an implementation defect to the original Worker (`Verifying → In Progress`), repair environment / integration conditions then reverify, return invalid Task Contract to planning as `Blocked`, and return requirement / design defects upstream as `Blocked`. If attribution is unreliable, enter Debug & Defect Resolution rather than guessing. A verifier capability problem is not an implementation defect.
- Convert a formal verdict to the target state: `passed → Done`, `repair_required → In Progress`, `blocked → Blocked`. Then commit only confirmed Result, Evidence, `code_ref`, Blocker, relevant Findings, dependency updates, Runnable updates, Requirement Sync facts, and next action to the existing facts. Do not retain worker logs or reasoning as long-term facts.
- A blocked dependency makes a downstream Ready Task non-Runnable; it does not fabricate a downstream `Blocked` status. When all `TasksOf(REQ-xx)` are Done, perform Requirement Integration, then its AC Gate, then Requirement Push to the remote development branch. Push is not Merge, Release, Deploy, or final Verified. On failure retain confirmed task facts, route to the shortest correction path, and recompute Runnable. Schedule event-driven rather than fixed Waves.

## Stage 06 — independent verification and closure

- Establish a final verification baseline from the complete change set, task / requirement results, evidence, code references, applicable rules, active Open Items, risks, actual environment, and final acceptance scope. Identify gaps, derive deterministic, independent-review, and Human-acceptance strategy appropriate to risk, then bind each to clear evidence.
- Verification is read-only with respect to the implementation being assessed. Run deterministic checks first. Execute multi-dimensional checks against the real verification object, preserve command / output / environment evidence, and keep reviewers fresh from implementation where practical. Do not weaken a pass condition or repair business code merely to make verification pass.
- A Finding is a fact with evidence, severity / impact, scope, owner, status, and correction path. Locate the earliest failed layer, route correction there, then reverify the affected scope. Keep Findings distinct from Open Items; unresolved or unreliable attribution goes through the Debug Exception Workflow.
- Close only when evidence is complete, traceable, and consistent with Requirement, AC, design, Task Contract, actual code reference, and final scope. Report `Verified` only for all passing required Gates with no unresolved blocking finding; report `Blocked` with the blocker, evidence, required decision / action, and resume point otherwise. Do not manufacture closure from activity, task commits, or requirement pushes.

## Repository release guard

The modeled target works on a feature branch. Do not merge to `main`, tag, release, or change version fields until the required deterministic checks, independent review, and release gate have passed. Verify this fixture through `python3 -m unittest discover -v`. The compiler state and reports under `.harness-state/` are evidence for this compilation, not a replacement for the Canonical documents.
