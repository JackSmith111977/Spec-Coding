# 3. System Definition｜系统定义

## 3.1 目标

基于 Business Definition，将业务模型转化为**最小充分的系统模型**，明确系统边界、核心职责、组件关系、数据归属及关键运行链路，为后续需求框架与技术方案提供稳定的系统上下文。

系统定义只回答“**系统需要如何承载业务**”，不在本阶段展开具体技术选型、接口细节、数据库字段或实现方案。

---

## 3.2 定义系统范围

从核心业务能力出发，明确项目需要由哪些系统、服务或主要模块承载。

```text
Business Capability
        ↓
System / Service
        ↓
Module
```

重点明确：

- 哪些能力属于项目内部系统。
- 哪些能力依赖外部系统或第三方服务。
- 核心系统、服务或模块各自承载什么职责。
- 系统边界在哪里，哪些内容明确不由当前系统负责。

> 优先定义系统职责与边界，不以技术栈或代码结构代替系统范围。

### 启发式引导

- 每项核心业务能力由谁承载？
- 哪些能力必须由当前系统负责，哪些可以依赖外部能力？
- 当前讨论的是系统职责，还是已经进入具体实现设计？

---

## 3.3 定义系统要素

### 1. 组件与职责

明确主要系统、服务或模块各自负责什么、不负责什么、彼此如何协作，并检查职责是否重叠或缺失。粒度保持在系统、服务或主要模块层级。

### 2. 交互边界

明确谁调用谁、哪些交互同步完成、哪些过程适合异步、哪些能力通过外部系统完成。本阶段只定义关键交互关系，不设计完整 API 契约。

### 3. 数据归属

将核心 Business Object 映射到系统职责中，明确：

- 谁创建。
- 谁修改。
- 谁持有或持久化。
- 谁消费。
- 数据在关键场景中如何流转。

> 只定义数据职责与归属，不提前设计数据库表、字段或存储实现。

### 4. 约束与设计假设

区分：

- `Constraint`：已知且必须遵守的外部约束。
- `Design Assumption`：当前用于推进系统定义、但仍可能调整的设计判断。

尚未确认的重要判断应显式保留，不将早期假设固化为系统事实。

---

## 3.4 定义系统运行链路

```text
Business Scenario
       ↓
System Entry
       ↓
Control Flow
       ↓
Data / State Change
       ↓
Sync / Async Boundary
       ↓
System Result
```

重点明确业务入口、参与组件、数据流转、状态变化、同步 / 异步边界与最终系统结果。

对于复杂链路，可按需补充 Sequence Diagram（时序图）、Data Flow（数据流）或 State Machine（状态机）；简单场景不强制建模。

> 优先保证核心业务场景能够端到端跑通，再补充非核心分支。

---

## 3.5 校验并固化系统定义

### 1. 业务覆盖

```text
Business Capability
        ↓
System Responsibility
        ↓
System Flow
```

不存在“业务已定义，但系统中无人承载”的关键能力。

### 2. 模型自洽

重点检查职责重叠或缺口、数据归属、核心场景闭环、状态责任方、循环依赖、同步 / 异步边界与外部依赖边界。

### 3. 控制设计深度

若讨论进入以下内容，应判断是否已经超出本阶段：

- 具体技术框架与基础设施选型。
- API 路径、请求结构或协议细节。
- 数据库表、字段与索引设计。
- 类、函数或代码组织方式。
- 部署拓扑与工程实现细节。

除非这些内容已经是明确约束，否则应留给后续技术方案处理。

---

## 3.6 结构化产物

| 章节 | 内容 |
|---|---|
| `System Scope` | 系统边界、核心系统或服务、外部依赖。 |
| `System Model` | 组件职责、交互关系、数据归属及关键约束。 |
| `System Flows` | 核心场景对应的控制流、数据流、状态变化及同步 / 异步边界。 |
| `Assumptions / Open Items` | 尚未确认但会影响后续设计的重要系统判断；无则省略。 |

---

## 3.7 完成标准

当新的 Human 或 Agent 仅依赖 System Definition，即可说明系统边界、核心承载组件、职责、数据流、核心端到端链路、同步 / 异步边界、约束与开放项时，本阶段完成。

---

## 3.8 下游使用约定

System Definition 是新建项目定义阶段的**系统语义层产物**。

```text
Business Definition
        ↓
System Definition
        ↓
Requirement Framework
        ↓
Requirement Clarification
        ↓
Technical Design
```

因此，System Definition 的最终职责是：

> **将业务模型转化为最小充分且自洽的系统模型，使 Human 与 Agent 对“系统如何承载业务”形成一致认知。**
