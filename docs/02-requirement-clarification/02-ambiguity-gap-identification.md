# 2. Ambiguity & Gap Identification｜歧义与缺口识别

## 2.1 目标

基于 Requirement Interpretation，识别当前需求理解中可能影响需求正确性、范围判断、业务规则或后续技术设计的不确定项，并将其转化为**最小、明确、可回答的澄清问题**。

本步骤不追求消除所有未知，只处理**会影响后续决策的关键不确定性**。

---

## 2.2 识别不确定项

重点检查：

- **Ambiguity｜歧义**：同一描述存在多种合理解释。
- **Gap｜缺失**：关键条件、规则或场景尚未定义。
- **Conflict｜冲突**：不同需求材料、现有行为或上下文之间存在矛盾。
- **Assumption｜假设**：当前判断依赖尚未确认的前提。

优先从 Requirement Interpretation 中的 `Inference`、`Unknown`、`Problem` 与 `To-Be` 开始检查，不重新执行完整需求解读。

---

## 2.3 筛选关键问题

判断原则：

> **如果不确认该问题，是否会影响需求正确性、范围、业务规则或后续技术决策？**

```text
发现不确定项
      ↓
是否影响后续决策？
   ↙       ↘
 否         是
忽略       进入澄清
```

不影响当前决策的细节可以暂时保留，不应为了“信息完整”增加无意义的澄清成本。

需要继续跨阶段承接的问题应进入 Open Item（开放项）生命周期；已有上游 `OI-xxx` 时直接复用，不重新创建副本。

---

## 2.4 形成澄清问题

好的澄清问题应尽量：

- 指向明确场景。
- 聚焦单一不确定点。
- 能得到明确结论。
- 必要时附带当前理解或候选选项，降低沟通成本。

例如：

```text
不推荐：
重新上传的逻辑是什么？

推荐：
用户重新上传同一对象后，
是否覆盖已有数据，还是保留历史版本？
```

澄清问题只负责确认需求事实，不提前讨论具体技术实现。

---

## 2.5 歧义与缺口识别产物

只保留对后续决策有实际影响的问题。需要持续跟踪时，按全局 Open Item Contract 使用稳定 `OI-xxx`：

| 字段 | 内容 |
|---|---|
| `ID` | `OI-xxx`；已有上游 Open Item 时沿用原 ID。 |
| `Issue` | 当前存在的歧义、缺失、冲突或假设。 |
| `Impact` | 若不确认，会影响什么后续决策。 |
| `Question` | 对应的最小澄清问题。 |
| `Status` | `open` / `resolved` / `deferred`。 |
| `Blocking` | 是否阻塞当前需求继续推进。 |
| `Owner Stage` | 当前应负责继续处理该问题的阶段。 |
| `Resolution` | 已解决时记录最终结论与必要依据；否则省略。 |

低价值未知不必创建 `OI-xxx`；`deferred` 只用于明确决定后移且已有承接位置的事项。

---

## 2.6 完成标准

当 Human 或 Agent 能清楚回答当前有哪些关键不确定项、哪些会影响后续决策、是否已转化为明确可回答的问题，需要跨阶段承接的 Open Item 是否具有稳定 ID / 状态 / 承接位置，以及是否排除了低价值问题时，本步骤完成。

---

## 2.7 下游使用约定

```text
Requirement Interpretation
          ↓
Ambiguity & Gap Identification
          ↓
Clarification List / OI-xxx
          ↓
Scope & Rule Confirmation
```

下游继续处理未关闭问题时引用同一 `OI-xxx`，不得通过复制问题描述形成新的事实源。

因此，本步骤的最终职责是：

> **识别会影响后续决策的不确定项，将其压缩为最小、明确、可回答的澄清问题，并为需要跨阶段承接的问题建立稳定 Open Item 身份。**
