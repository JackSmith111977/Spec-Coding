# Code Quality Rules｜代码质量规则

本文件定义所有代码产物默认适用的通用质量原则，重点降低 Human / Agent 的理解、评审与后续维护成本。

本规则不规定具体语言、框架、架构层次、代码组织方式或格式细节。若更换语言、框架或系统形态后某条规则不再成立，则不应将其作为本文件的核心规则。

---

## 1. Understandability｜可理解性

目标：**让读者以尽可能少的回读、跳转和推断建立正确心智模型。**

- 主执行路径应容易识别，代码顺序尽量符合人的逻辑理解顺序。
- 减少无意义的 Backtracking（回读）与 Context Switching（上下文切换）。
- 命名应表达当前上下文中的角色、意图或结果，减少依赖额外推断的模糊表达。
- 复杂逻辑可通过有意义的中间语义降低认知负担，而不是仅做形式拆分。
- 关键状态变化、重要副作用、影响正确性的默认行为与当前层必须承担的失败行为应具有足够可见性。
- 显式性以帮助正确理解为目标，不要求展开所有实现细节。

> **Optimize for comprehension, not appearance｜优化理解成本，而不是形式上的整洁。**

---

## 2. Information Quality｜信息质量

目标：**代码与注释共同提供高价值、低噪声、长期有效的信息。**

### 代码与注释边界

- 简单逻辑优先由代码自身表达，不用注释重复显然行为。
- 名称承担持续复用的语义；注释补充代码难以自然表达的非显然上下文。
- 注释应降低未来理解或错误修改成本，而不是证明实现过程完整。

### 注释粒度

注释粒度与理解难度匹配，而不是与代码长度机械绑定：

```text
简单 / 直观逻辑
→ 代码自解释为主，必要时使用函数 / 整体说明

存在独立复杂步骤或流程
→ 块级注释帮助建立局部心智模型

关键局部行为非直观、容易误解或误改
→ 必要的行级注释
```

### 信息稳定性

优先保留当前仍然有效、且缺失后可能导致误解或错误修改的信息，例如 Constraint（约束）、Invariant（不变量）或非直观决策原因。

以下一次性历史信息默认不进入持久代码注释：

- 过去采用过什么实现；
- 本次如何从旧方案改为新方案；
- 为某次需求删除或替换了什么；
- 已可通过 Requirement / Design / Task / Commit / PR 稳定追溯的变更历史。

如果历史原因仍然形成当前不可破坏的约束，则只保留**当前约束及必要原因**，不展开历史叙事。

> **Comment for comprehension, not for history｜注释服务当前理解，不保存变更历史。**

---

## 3. Change Clarity｜变更清晰度

目标：**让 Reviewer 快速识别本次真实语义变化，并把注意力集中在受影响范围。**

- 变更围绕当前 Requirement / Task 聚焦，不因发现其他问题而默认扩张范围。
- 不顺手进行与当前目标无关的清理、重命名、格式调整或重构。
- 减少与真实语义变化无关的 Diff Noise（差异噪声）。
- 未受当前需求影响的代码尽量保持稳定。
- 优先形成 Smallest Coherent Change（最小完整变更）：完整覆盖当前目标所需变化，但不机械追求最少修改行数。
- 必要结构调整不应掩盖真正的行为变化；Reviewer 应能够区分结构变化与语义变化。
- 一次性变更说明属于 Task / Commit / PR 等变更事实源，不残留为持久代码注释。

> **Focused, coherent, low-noise change｜聚焦、完整、低噪声。**

---

## 4. Consistency｜一致性

目标：**让新增或修改后的代码自然融入当前项目，减少无意义的风格与语义漂移。**

- 修改前先识别当前项目、模块和相邻实现已经形成的稳定表达。
- 同一概念已有稳定 Vocabulary（项目词汇）时优先复用，不无理由创造同义表达。
- 在不降低代码质量的前提下，沿用项目已有命名、注释和表达惯例。
- Code Quality Rules 决定“什么信息和质量需要保持”，项目惯例决定“这些信息具体如何表达”。
- 明显降低正确性、可理解性或可维护性的旧模式不应继续扩散；但不因发现技术债而默认进行无关治理。

> **Respect conventions without propagating defects｜尊重稳定惯例，但不扩散明显问题。**

---

## 5. 使用约定

本文件是跨阶段 Rule（规则），不是独立 Workflow（流程）阶段，不产生新的状态流转或阶段产物。

主要消费位置：

- **Development Execution｜开发实施**：Worker 在项目已有约束和 Task Contract 内实施时遵守适用规则。
- **Verification Convergence｜验证收敛**：对机器难以判定的可理解性、信息质量、变更清晰度与一致性，通过 Independent Review（独立审查）按风险验证。

具体项目可以将这些原则映射为 Rule / Instruction、Formatter / Linter、Static Analysis、Checklist、Fresh Reviewer、CI Gate 等 Harness 机制，但不得把某一种语言、框架或工具的实现方式反向固化为本文件的通用规则。

> **Stable principles, context-specific enforcement｜原则保持稳定，执行方式由项目上下文决定。**
