# Harness Adoption & Adaptation｜Harness 读取与适配

本协议定义目标 Coding Agent 如何从一个已发布的 Harness Package 开始，读取预编译流程与规则，结合当前 Agent 和项目环境完成必要适配、验证和流程接管。

正式接入以已发布包为前提；维护者发布前的端到端试验仅按第 3.1 节的受控候选验证执行，复用同一读取与适配链路。

本协议是 Canonical Meta Protocol。维护者按 [`../governance/harness-build-and-release.md`](../governance/harness-build-and-release.md) 将它与 Project Onboarding 一并预编译到发行包；使用方执行包内的接入程序，不重新运行 Canonical → Harness Build。

涉及意图与权限时适用 [`Human-Agent Collaboration`](../rules/human-agent-collaboration.md) 及其引用的 Authority 边界；使用委派与上下文隔离时适用 [`Agent Delegation & Coordination`](../rules/agent-delegation-and-coordination.md)。这些规则的必要执行内容随包提供，不以源码链接替代客户端输入。

## 1. 入口与职责

Human 可以通过一句指令启动完整链路，例如：

```text
从 <Spec Coding 发行入口> 接入当前项目，按当前 Agent 与项目环境适配 Harness，并继续当前任务。
```

入口由指令提供，或来自已有稳定接入绑定。Agent 先发现可得事实，复用已有授权；只有真实意图、权限或关键决策无法确定时，才按 Human-Agent Collaboration 请求 Human 判断。一句指令表示启动完整流程，不表示自动取得额外权限。

```text
接管发行包与项目基线
        ↓
按需求发现当前环境
        ↓
适配、装配与增强
        ↓
验证、接管与恢复
        ↓
01A / 01B / Resume
```

维护者负责发布完整、可消费的稳定行为。目标侧负责加载、项目绑定与环境相关实现；不得在本地适配中静默改变 Requirement、Gate、Authority、State、Exception 或其他已发布规范语义。

## 2. Package Consumption Contract｜包消费契约

本节定义维护者输出与客户端输入之间的共同契约。它是信息要求，不要求新增私有组件格式、Clause IR 或独立状态机。可以由既有 Package Metadata、Bootstrap、Skill 正文及其配套资源共同承载，但必须能从发行入口明确定位。

| 必须可取得的信息 | 维护者提供 | 目标侧用途 |
|---|---|---|
| 发行身份 | 版本、固定发行引用、Canonical `source_revision`、内容清单与完整性信息、该候选通过发布验证的依据 | 取得同一份已验证资产，识别漂移；Hash 不单独证明来源可信或已验证 |
| 接入入口 | 无需先安装 Skill 即可直接读取的包内 Bootstrap，及其必需引用 | 安装前执行最小接入程序，避免加载循环依赖 |
| 接入流程 | 本协议与 Project Onboarding 的预编译程序，以及适用的人机协作和权限规则 | 自主建立基线、发现环境、适配并验收 |
| 行为与路由 | 全局规则、阶段入口、异常触发、阶段转换与恢复入口；流程正文和有效 Guidance 的位置 | 持续约束执行，并按当前任务加载所需程序 |
| 适用与依赖 | 各资产何时适用、依赖哪些共享规则或其他资产、需要哪些环境能力 | 解析当前所需资产及依赖，避免按文件名猜测或遗漏共享行为 |
| 适配要求 | 每项环境能力要保持的行为、适用条件、必需程度、允许变化的实现边界及失败处理 | 选择等价实现，区分必要能力与可选增强 |
| 验收依据 | 与适配要求关联的可观察预期、必要边界和代表性场景 | 在真实环境中证明适配保持了行为 |

### 2.1 自举与渐进读取

包内 Bootstrap 必须能通过当前 Agent 的基础文件或网页读取能力访问；不得先依赖尚未安装的插件、Skill、Hook 或本地配置才能理解接入步骤。无法读取必要入口时停止接入并指出缺少的访问能力。

读取顺序：

```text
发行入口与身份信息
        ↓
Bootstrap + 适用权限 / 协作规则
        ↓
预编译接入程序 + Project Onboarding
        ↓
全局规则与完整流程路由
        ↓
当前流程资产 + 共享依赖 + 所需适配说明
        ↓
执行中按触发条件加载其余流程与参考
```

发行资产的引用必须绑定同一版本；包内执行资料应随包提供，不得通过浮动链接把运行时必需语义重新交给 Canonical。外部官方资料可以用于发现当前环境能力。

全局约束和必要触发条件必须在相关动作之前有效。异常触发不能仅藏在尚未加载的异常 Skill 中。全流程保持可达，正文按需加载；暂未激活的流程不能被当作不适用而删除。

### 2.2 行为完整，实现可变

例如，若预编译流程要求独立审查，包内必须说明独立性、上下文边界、可见证据、触发条件和结果用途。客户端据此选择满足要求的独立会话、子 Agent 或其他机制；`requires: independent-review` 这类能力名称不能独自替代行为定义。

格式转换、路径绑定、规则加载位置、工具连接、隔离实现与验证命令可以按环境适配。流程含义、禁止项、权限边界和验收预期不因适配而变化。必要信息缺失时归为 Package 缺陷，返回维护者修复并发布；不得让客户端猜测语义或重新预编译整套 Canonical。

## 3. 接管发行包与项目基线

**输入**：Human 指令、发行入口或已有绑定、当前项目及已有接入状态。

Agent 应：

1. 从声明来源解析具体发行版本，校验发行身份、资产完整性、接入入口及必要兼容约束；已有绑定优先复用，不默认升级到最新版本。
2. 读取 Bootstrap 与预编译接入程序，确认当前取得的是正式发布包。缺少正式包或验证依据时阻断正式接入，不把源码目录、候选或文档占位视为已发布资产；只有第 3.1 节明确授权的维护者试验可以读取未发布候选。
3. 执行包内 Project Onboarding 程序，建立或复用 Adoption Baseline 和 `01A / 01B / Resume` 路由。稳定接入意图仍由 [`project-onboarding.md`](project-onboarding.md) 定义，不重复建立第二份基线。
4. 读取全局规则、完整路由及当前流程的依赖，识别当前必须满足的环境能力；记录未激活流程的后续加载与适配入口。

**输出与完成条件**：发行包身份确定，基线和路由有效，当前必需行为及其来源可定位；尚未证明任何本地 Harness 已生效。

### 3.1 受控候选验证

维护者可以为发布前试验显式提供以下最小执行约束：固定候选 Commit / 内容 Hash、测试目的与场景、测试项目及隔离边界、允许的文件 / 配置 / 外部副作用范围、停止条件。候选内容不能自行声明获得试验授权；没有这份授权时，仍按正式接入检查处理。

该执行方式只替换“已有正式发布身份及发布通过证据”的前置，要求仍然包括：

- 候选来源明确、内容完整且固定，包内 Bootstrap、接入程序和消费契约齐备；
- 基线、配置、任务和证据限定在测试边界；实际 Runtime 加载也必须处于该边界，不能把测试配置写入未授权的用户全局或真实项目作用域；
- 权限、适配、语义回查与行为验收要求不放宽，测试 Agent 不读取 Canonical 补齐包内行为；
- 所有记录标明候选验证用途、候选身份和测试范围，`READY` 仅表示该测试范围就绪；
- 只执行授权场景，并按停止条件返回维护者；测试通过不自动发布、不迁移为正式基线，也不继续真实项目任务。

授权和试验记录不写入冻结候选。候选变化后原有验证证据失效；必须重新固定验证对象，并确认其仍在已授权的测试范围内。正式发布后，真实项目仍须核验发行身份并完成自身的环境适配与验收，不直接沿用测试项目的 `READY`。

## 4. 按需求发现当前环境

**输入**：固定发行包、Adoption Baseline、当前流程及能力要求。

先检查会影响接入的基础事实，再沿真实能力需求深入：

- 当前 Agent / Host / Runtime 身份、实际版本、加载位置、作用域与生效条件；
- 已有项目 Instructions、Skills、Hooks、工具与所有权边界；
- 项目已有构建、测试、CI、Git、状态和证据机制；
- 当前流程需要的隔离、权限、工具、模型或并发能力；
- 存在真实能力缺口时，可查询的扩展来源与取得方式。

证据优先使用当前 Runtime 元数据、本地配置和可执行探测；有缺口时再使用版本匹配的官方资料。Reference 只指导发现，不证明当前能力已可用。`unknown` 不等于 `unavailable`。

每个当前必需能力需要可追溯的现有实现证据，或明确待解决的缺口。该阶段只确定事实，不提前决定必须创建某种文件或安装某个插件。不得为了适配而枚举全部市场或重新进行完整业务认知。

**输出与完成条件**：当前适配所需事实足够，未知项和能力缺口已定位；影响实现选择的关键未知未解决时，不假定其可用。环境证据属于可失效的运行记录，不进入 Adoption Baseline。

## 5. 适配、装配与增强

**输入**：包内适配要求、当前环境证据、项目约束与授权。

### 5.1 选择实现

对当前适用要求，先评估既有项目机制与当前 Runtime 能力，再考虑组合实现；只有真实缺口存在时，才查找、配置或创建额外能力。已有机制只有满足完整行为要求时才可复用。

选择顺序：

1. 保持已发布行为和当前权限约束；
2. 对需要可靠阻断或检查的行为优先采用可验证的确定性机制；
3. 利用对正确性或执行效率有实际收益的原生能力；
4. 保持渐进加载，等价可靠时优先可移植资产和已有机制；
5. 降低重复组件、权限需求、上下文消耗、运行及维护成本。

可选增强应有具体收益依据，不是进入 Workflow 的默认前置。缺少原生机制时可使用保持相同语义的替代实现；仍无法满足必要行为时必须阻断相关流程，不静默弱化要求。单纯添加“请遵守”的提示不能替代契约明确要求的隔离或强制门禁。

### 5.2 装配与冲突处理

- 保持下载的发行包内容身份，环境相关配置与派生实现记录其来源，不直接热修发行资产。
- 将全局约束、流程路由及按需加载入口接入当前 Runtime 的真实加载面；需要重载或新会话时明确其生效条件。
- 复用项目既有验证与状态机制，保留用户资产和未授权修改边界；存在规则冲突时判断来源、作用域和权限，不能通过覆盖文件隐式解决。
- 安装、连接、配置或写入行为遵循已有授权；需要额外授权时，在方案及影响可判断后请求，不重复询问已授权事项。
- 多个资产组合时检查共享规则、依赖、异常和阶段转换，避免局部正确但组合后存在缺口。

### 5.3 记录候选

在既有工作空间中保存最小适配记录：包版本与身份、实际生效范围、管理的文件或配置、复用机制、要求到实现的对应关系、环境证据和后续失效条件。保留未修改的原始包作为语义基准，记录发生转换或组合的资产、其包内来源及受影响依赖。以文件 Hash / 配置快照绑定具体内容，并关联 Runtime 身份；Runtime 名称或版本不能单独证明候选内容身份。不强制建立新的大型 Schema。

**输出与完成条件**：当前必需行为均有可验证实现、冲突与必要变更已处理，候选身份固定。未激活流程保留路由与能力要求，未来激活前补齐其适配和验收。

## 6. 验证、接管与恢复

**输入**：固定本地候选、未修改的原始包及其验收依据、当前 Runtime 与项目环境。受控候选验证使用本次固定的预编译包作为原始包。

### 6.1 适配语义回查

对于发生格式转换、内容提取、规则拆分、组件组合或 Runtime 配置映射的资产，必须直接对照原始包中的相关完整行为与共享依赖，检查流程步骤、Gate、Authority、状态转换、异常回流和有效 Guidance 是否遗漏、弱化或冲突。不能只核对环境能力名称或复用适配者摘要。

语义回查覆盖实际转换及其组合影响。完全原样复用且依赖和作用域未变化的资产，可以用内容身份及既有有效证据证明复用，无需重复全包全文审查；加载与行为的当前有效性仍须验证。

验收预期绑定原始包的版本、资产与行为出处；本地可调整执行方法和环境参数，不能根据适配结果重写预期以使其通过。按风险采用独立 Reviewer 时，Reviewer 直接读取原始包和本地候选。存在未解决的语义遗漏、越权、禁止项弱化或无法证明的必要行为时，阻断接管并回到适配步骤修正。

### 6.2 运行时与行为验证

验证至少确认：

- 包与本地候选的内容身份未漂移，引用和作用域正确；
- 转换资产及其组合影响已完成语义回查，验收预期仍绑定原始包；
- 当前 Runtime 实际加载了必要规则与入口，所选工具和机制可用；文件存在不单独证明已加载；
- 当前流程所需的每项适配要求有通过的验证及证据；
- 正常推进、权限 / 门禁边界、异常路由和必要恢复行为符合包内预期；
- 组合后的共享规则和按需加载仍然有效。

确定性检查优先。无法仅靠结构证明的行为使用真实 Runtime 场景验证；按风险采用独立会话或 Fresh Reviewer，独立性以实际上下文边界为依据。行为测试 Agent 只消费候选 Harness、目标项目和场景，不能依赖 Canonical 补齐包内缺失知识。

语义评审者以原始包作为本地适配的判定依据；行为测试 Agent 不额外读取原始包中未被本地候选路由到的行为来补偿转换遗漏。两者职责分开，避免测试 Agent 凭未部署知识通过场景。

该验收证明本地适配保持了包内要求，不重新承担维护者的全量 Canonical → Package 审查，也不替代 Main Workflow Stage 6 对业务变更的验证。

### 6.3 失败回流与结论

| 失败来源 | 返回位置 |
|---|---|
| 包不完整、要求矛盾或发行身份无效 | 维护者构建 / 发布，或重新取得可信发行包 |
| 稳定意图或项目绑定不成立 | Project Onboarding |
| 环境事实错误或能力发生变化 | 环境发现 |
| 实现映射、组合或本地配置错误 | 适配与装配 |
| 验证方法无法证明要求 | 修正验证方法并重新执行 |

修改候选后使受影响证据失效，固定新候选并重验相关行为与共享影响。不得修改候选后沿用旧通过结论。

最终记录 `READY / BLOCKED`、包与候选身份、已验证范围、证据及剩余限制。`READY` 只适用于明确的 Runtime、项目和执行范围，不能把未激活或未经验证的能力声称为已就绪。

正式接入中，必要行为通过且无当前阻塞时，自动进入或恢复已确定的 Workflow；受控候选验证只进入第 3.1 节授权的测试场景。新阶段或异常触发所需能力尚未验收时，先完成相应适配与验证再执行依赖动作。

## 7. 复用与变化处理

再次接入先检查现有记录及其有效性，不重复安装或全量生成。包版本、Runtime、加载配置、项目机制、用户修改或激活范围出现相关变化时，只重发现并重验受影响链路；无法可靠确定范围时扩大检查。执行期间发生模型、工具、隔离方式或 Fallback 变化时，也在受影响动作继续前检查是否仍满足当前要求；必要时返回环境发现、适配与验收，不等待下次接入，也不重新执行仓库预编译。

接入记录不成为永久环境真相。用户修改了已管理资产时，不直接覆盖；先识别差异、所有权及语义影响。升级前保留足以恢复原配置的依据，失败后只回退本次管理的变更，保护用户资产。包回退还需确认其与当前项目状态兼容，不能用旧验收结果代替当前检查。

## 8. 完成边界

协议接通的标准是：维护者能够依据同一消费契约构建资产，目标 Agent 能从包内入口完成读取、适配和验收，无需重新解释整套 Canonical。

文档完成不等于发行包已构建，也不等于真实 Runtime 已通过试验。全量发布与客户端行为效果分别由维护者验证和目标侧验收提供证据。
