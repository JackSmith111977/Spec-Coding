# 1. Project Positioning｜项目定位

## 1.1 目标

从初始想法出发，逐步明确**项目为什么存在、主要为谁解决什么问题、希望创造什么核心价值，以及项目的基本目标与边界**，形成后续业务定义可直接复用的项目级语义基础。

项目定位只回答“**这是一个什么项目、为什么值得做、主要解决什么问题**”，不在本阶段展开具体业务流程、功能清单、系统架构或技术方案。

---

## 1.2 明确核心问题

从初始想法或已有方案描述中回溯项目真正需要解决的问题，避免直接以某个功能、产品形态或技术手段代替问题本身。

### 1. 需要确认的信息

- 当前存在什么核心问题或未满足需求。
- 谁会直接受到该问题影响。
- 问题通常发生在什么情境下。
- 当前通常如何解决，主要不足是什么。
- 为什么该问题值得通过一个独立项目解决。

### 2. 启发式引导

- 如果不做这个项目，用户会如何解决问题？
- 如果只能解决一个问题，最值得解决的是什么？
- 当前描述的是“问题”，还是已经预设好的“解决方案”？

启发式只用于帮助收敛问题，不要求逐项回答。

---

## 1.3 定位用户与场景

将核心问题落到具体使用者和典型场景中，回答“**谁在什么情况下，希望完成什么目标**”。

### 1. 用户与角色

- 识别最直接受益或使用项目的核心用户。
- 明确不同角色与项目之间的主要关系。
- 暂不展开详细权限、组织关系或业务职责。

### 2. 典型场景

- 明确问题最典型的发生场景。
- 明确用户在场景中的主要目标。
- 优先描述真实使用过程，而不是直接枚举功能。

```text
User / Role
    ↓
Context / Problem
    ↓
User Goal
```

当用户或场景过于宽泛时，优先收敛到最能代表项目核心价值的一类用户和场景。

---

## 1.4 明确价值、目标与边界

### 1. 核心价值

核心价值优先描述**用户使用前后的关键变化**，而不是系统拥有了哪些功能。

```text
Before
  ↓
Project
  ↓
After
```

重点回答：用户当前处于什么状态、项目希望改善什么、如果只能创造一种核心价值那是什么。

### 2. 项目目标

- 用项目级语言描述最终希望建立的整体能力。
- 目标应能够支撑后续业务定义，但不提前拆解为功能列表。
- 避免使用接口、模块、技术栈等实现方式描述项目目标。

### 3. 基本边界

- 明确项目主要负责什么。
- 明确哪些相关内容当前不属于项目本身。
- 对仍无法确定的边界显式保留，不通过默认假设强行补全。

边界只控制项目方向和基本范围，具体 In Scope / Out of Scope 仍由后续需求澄清确认。

---

## 1.5 固化项目定位

### 归纳原则

- 保留能够稳定项目方向的最小充分信息。
- 从问题、用户和价值出发，不以功能清单代替项目定义。
- 区分已确认定义、合理假设与待确认信息。
- 未验证但影响项目成立的关键判断显式保留。
- 不提前解决业务定义、系统定义或需求澄清的问题。

### 结构化产物

| 章节 | 内容 |
|---|---|
| `Identity` | 项目名称、定位与一句话定义。 |
| `Problem` | 核心问题及当前不足。 |
| `Users & Scenarios` | 核心用户、角色与典型场景。 |
| `Value` | 项目希望创造的核心用户 / 业务价值。 |
| `Goals` | 项目级目标与整体能力。 |
| `Boundaries` | 基本职责边界与明确不做的内容。 |
| `Assumptions / Open Items` | 尚未确认但影响项目成立的重要判断；无则省略。 |

---

## 1.6 完成标准

项目定位不以“把想法全部细化”为完成标准。

当一个未参与前期讨论的人或新的 Agent 仅依赖 Project Positioning，即可快速回答以下问题时，本阶段完成：

- 这个项目是什么，为什么要做？
- 主要为谁解决什么问题？
- 典型使用场景是什么？
- 项目希望带来什么核心变化？
- 项目最终希望建立什么整体能力？
- 当前主要负责什么、明确不做什么？
- 是否存在影响项目成立的重要假设或开放项？

---

## 1.7 下游使用约定

Project Positioning 是新项目定义阶段的方向基线。后续 Business Definition 应直接基于已确认的问题、用户、场景、价值、目标与边界建立业务模型，不重新从模糊想法推断项目方向。

```text
Project Positioning
        ↓
Business Definition
        ↓
System Definition
        ↓
Requirement Framework
        ↓
Requirement Clarification
```

因此，Project Positioning 的最终职责是：

> **将模糊想法收敛为最小充分、边界清晰的项目定义，使 Human 与 Agent 对为什么做、为谁做、解决什么、创造什么价值形成一致认知。**
