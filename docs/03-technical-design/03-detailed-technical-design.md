# 3. Detailed Technical Design｜方案详细设计

## 3.1 目标

基于已确认的 Solution Decision，将选定方案展开为足够指导实施的系统设计，明确系统结构、关键运行链路、模块契约以及必要的异常与边界处理。

本步骤重点回答：

> **选定方案具体如何落到系统中，各部分需要怎样协作。**

设计应达到能够稳定指导后续任务拆解与实现的粒度，但不提前展开到具体代码文件、函数拆分或实现步骤。

---

## 3.2 结构展开

重点确认：

- 哪些模块需要新增、修改或复用。
- 各模块承担什么职责。
- 模块之间的边界与协作关系如何变化。
- 哪些现有职责和系统边界保持不变。

设计应优先复用既有架构与扩展机制，避免为了当前需求无必要地扩大系统改造范围。

---

## 3.3 链路设计

```text
Trigger
   ↓
Input
   ↓
Processing
   ↓
Data / State Change
   ↓
Dependency
   ↓
Result
```

重点设计：

- **Interaction Flow｜交互链路**：页面、接口、服务或模块之间如何协作。
- **Data Flow｜数据流**：关键数据如何产生、传递、转换与持久化。
- **State Flow｜状态流**：关键状态如何变化，以及由什么事件触发。
- **Async / Timing｜异步与时序**：存在异步、事件或并发时，明确关键时序关系。

只描述影响需求实现的关键链路，不展开与本次变化无关的完整系统流程。

---

## 3.4 契约设计

根据实际需求选择定义：

- API / RPC 接口。
- Request / Response 数据结构。
- Event / Message 结构与语义。
- 数据模型与 Schema 变化。
- 状态定义与状态转换规则。
- 错误语义与返回约定。
- 权限、校验及其他跨边界规则。

契约设计应保证不同模块能够基于一致约定独立实现和验证，避免关键语义留到编码阶段再临时决定。

---

## 3.5 边界补全

重点关注：

- 失败与异常处理。
- 超时、重试与幂等性。
- 并发与状态冲突。
- 旧数据或旧接口兼容。
- 发布、迁移与回滚要求。
- 权限、安全或极端输入边界。

只处理会实际影响当前方案正确性和可交付性的边界，不为了形式完整性无限扩展异常场景。

---

## 3.6 详细设计产物

| 内容 | 说明 |
|---|---|
| `Structure` | 涉及的模块、职责及边界变化。 |
| `To-Be Flow` | 关键交互、数据、状态及时序链路。 |
| `Contracts` | 需要稳定下来的接口、数据与状态约定。 |
| `Boundary Handling` | 与当前方案相关的异常、兼容和运行边界。 |
| `Open Issues` | 尚未解决、但不阻塞主体设计的问题；无则省略。 |

根据需求复杂度按需展开，不要求每个项目都具备所有章节。

---

## 3.7 完成标准

当 Human 或 Agent 能回答模块职责变化、核心 To-Be 行为、关键数据 / 状态 / 调用链、跨模块契约、重要异常 / 兼容边界，并确认粒度足以任务拆解又未下沉到代码实现计划时，本步骤完成。

若核心方案无法成立，应返回 Solution Design & Decision；若需求或约束认知偏差，则沿追溯链回到对应上游阶段纠正。

---

## 3.8 下游使用约定

```text
Solution Decision
       ↓
Structure Design
       ↓
Flow Design
       ↓
Contract Design
       ↓
Boundary Design
       ↓
Detailed Technical Design
       ↓
Task Planning / Implementation
```

因此，本步骤的最终职责是：

> **将已选技术方案展开为清晰、完整且可实施的系统设计，使后续实现建立在一致的结构、链路、契约与边界认知之上。**
