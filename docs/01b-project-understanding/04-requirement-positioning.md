# 4. Requirement Positioning｜需求定位

## 4.1 目标

在 Business Context 与 System Context 基础上，将本次需求准确映射到现有业务模型与系统模型中，明确**需求希望改变什么、变化发生在哪些业务场景与对象、由哪些系统组件和链路承载，以及需求与现状之间存在哪些明显差异或缺口**。

需求定位只回答“**变化发生在哪里、现状与需求哪里对不上**”，不在本阶段解决需求歧义，也不提前设计技术方案。

---

## 4.2 提取需求变化点

从原始需求中识别新增、修改、扩展、限制或移除的现有业务行为，将自然语言需求整理为可定位的 Change Points。

- 优先描述业务行为如何变化，避免直接转换为代码、接口、字段或组件修改。
- 一个变化点只表达一个相对独立的变化意图。
- 暂不补全需求中尚未明确的目标行为。

```text
As-Is Behavior
  ↓
Change Intent
```

本步骤只提取变化意图，不判断具体如何实现。

---

## 4.3 定位业务影响

重点确认：

- **参与者**：哪些角色的目标、职责或可执行行为受到影响。
- **业务对象**：变化作用于哪些核心业务对象或对象关系。
- **业务场景**：变化发生在哪个现有业务场景、阶段或动作附近。
- **状态 / 规则**：是否改变状态、前置条件、业务规则、权限边界或关键分支。

区分：

- **Direct Impact｜直接影响**：需求明确改变的业务行为、对象、场景或规则。
- **Adjacent Impact｜关联影响**：与直接影响存在上下游、消费或依赖关系，可能受到影响但尚未确认需要改变的部分。

关联影响只作为后续澄清和验证线索，不默认纳入需求范围。

---

## 4.4 定位系统影响

重点确认：

- **系统入口**：相关行为从哪个页面、接口、任务或事件进入系统。
- **核心组件**：哪些系统、服务或模块直接承载相关业务能力。
- **关键链路**：需求位于哪条现有 System Flow 中。
- **核心数据**：涉及哪些关键数据、状态及主要存储 / 消费位置。
- **系统边界**：是否跨越服务、同步 / 异步、存储或外部系统边界。

系统定位只确定 Change Surface，不决定具体修改哪些类、接口、字段或实现方式。

复杂需求可建立变化点—业务位置—系统位置的轻量映射表。

---

## 4.5 验证并固化需求位置

### Gap 识别

- **Existing Capability**：现有能力已经存在，本次主要扩展或调整。
- **Missing Capability**：需求依赖的业务或系统能力当前不存在。
- **Semantic Mismatch**：需求中的概念、行为或状态与现有业务语义不一致。
- **Boundary Conflict**：需求与现有业务边界、系统边界或运行方式存在明显冲突。

本阶段只负责发现和定位 Gap；目标行为到底是什么、Gap 如何解决交给后续需求澄清与技术方案设计。

### 验证原则

- 优先验证会影响需求范围或澄清方向的关键定位结论。
- 区分直接影响、关联影响和仍无法确认的潜在影响。
- 需求描述与现状不一致时，不默认任何一方正确。
- 不因发现某个系统落点就提前推导具体实现方案。

### 结构化产物

| 章节 | 内容 |
|---|---|
| `Change Points` | 从原始需求中提取的核心变化意图。 |
| `Business Position` | 变化涉及的参与者、对象、场景、状态 / 规则及 Direct / Adjacent Impact。 |
| `System Position` | 变化对应的系统入口、组件、链路、数据与系统边界及 Direct / Adjacent Impact。 |
| `Gaps` | 能力缺失、语义差异、边界冲突或其他待澄清问题。 |

Requirement Context 只保存相对 Business Context 与 System Context 新增的定位信息，避免复制既有模型和完整链路。

---

## 4.6 完成标准

新的 Human 或 Agent 仅依赖 Requirement Context，应能回答本次需求要改变什么、分别落在什么业务 / 系统位置、哪些属于直接 / 关联影响，以及现状与需求之间有哪些 Gap。

---

## 4.7 下游使用约定

```text
Project Overview
  ↓
Business Context
  ↓
System Context
  ↓
Requirement Context
  ↓
Requirement Clarification
  ↓
Technical Design
```

因此，Requirement Positioning 的最终职责是：

> **将原始需求准确放回已验证的业务与系统现状中，明确“要变什么、变在哪里、哪里对不上”，为后续需求澄清提供最小充分、可追溯的需求上下文。**
